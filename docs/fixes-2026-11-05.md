## 1. Search hits carry only the CID

**Seen:** `/mcp` `search` returned `id: "bafyrei…"` and no `statement_id`. CIDs change whenever
a record is re-shaped, so agents can't cite them (supports/refutes) durably. `get` accepted the
identity, `similar` didn't, and on a fresh isolate `similar` answered "not loaded" even for a
CID `get` would have found.

**Cause:** `briefOf` (`src/core/roles.js`) emits `id: row.id` only; `neighbors`
(`src/agent/tools.js`) and `similar` (`src/agent/view-tools.js`) match `r.id` only, and
`similar` never loads views when `loaded` is empty.

**Done (branch `fix/identity-in-briefs`):** briefs add `[roles.identity]: value` beside `id`
(additive: tools are a public interface); `neighbors` and `similar` resolve the identity;
`similar` loads like `get` on a fresh isolate. Self-check added in `tools.js`.

**Overhaul option:** make the identity *the* row id when declared (as the guide already claims,
see 8). Touches taste (likes keyed by id), the page's `#/item/<id>` routes, `rate`/`discover`,
and every view already shipped. Do it once, with a view-format version bump.

## 2. Domains the app no longer presents are never dropped

**Seen:** dev-intel's view served 18 other publishers' repos (`explorer-live-*`, `hello-test`, …):
three `records` checks failed at 64.5%, and agents searching the app saw them.

**Cause:** `--register` deploys the Worker with no sources, so `presentedRepos` is `[]`
("every repo") and the 5-minute cron indexes the whole network into R2. After the first full
ship presents only `0x…/dev-intel-test-0`, the drop loop in `updateView`
(`src/publish/view.js`, "What the app no longer presents is not served") skips any domain whose
repo *name* isn't in `repos` — meant to protect `--only` builds — so every foreign name stays.

**Fix:** pass `only` into `updateView`. On a full run, drop every domain not in `live`; on an
`--only` run, keep today's rule. And have `--register` deploy with the eventual presents (or
an explicit empty view) so the cron never indexes the network in the first place. Add a
self-check: register-shaped run (`[]`) then a full run (`[owner/x]`) leaves only `owner/x`.

**Cleanup by hand, if it recurs:** R2 keys are prefixed `view/`
(`view/cdn/domains/<d>/manifest`, `…/shards/<file>`), and `wrangler r2 object delete` reports
success on a key that doesn't exist, so a missing prefix deletes nothing silently. Delete, then
`westmarch-ship app.json --index` to rewrite the catalog.

## 3. `westmarch-lint` does nothing

**Seen:** `npx westmarch-lint https://…/view` exits 0 with no output.

**Cause:** the CLI guard in `src/publish/lint.js:350` requires `process.argv[1]` to end in
`/lint.js`; through `node_modules/.bin/westmarch-lint` it ends in `westmarch-lint`.

**Fix:** compare `realpathSync(process.argv[1])` with `fileURLToPath(import.meta.url)`, in every
file with this guard (grep `endsWith("/` across `src/`). Workaround: `node node_modules/@fangorn-network/westmarch/src/publish/lint.js <view>`.

## 4. A failed source reads as success

**Seen:** the source's `fangorn commit` failed; the log said `done: https://…` and only then
`✗ deployed, but these sources failed`. Through a pipe (`| tail`) the exit code was 0.

**Fix:** print the failure before `done`, and say `done (with failures)`; keep the non-zero
exit. Also print the source's stderr tail on failure — the real error (`unknown option '-m'`)
was only visible by rerunning the source by hand.

## 5. `.ship/repo` is behind the chain after the card is bound

**Seen:** after `--register`, `fangorn status` in `.ship/repo` said local HEAD ≠ on-chain tip:
`fangorn card --skip-register` committed `@card` without advancing that directory's head. A
source committing from there would build on a stale parent.

**Correction (found later):** a push from the stale copy can't clobber anything: the
DataRegistry reverts any update whose parent isn't the current head (`StaleStateRoot`). The
cost is a failed publish, not lost data.

**Fix:** have ship run the card bind in `.ship/repo` (or re-clone after it), and have sources
that share the app's repo run `fangorn clone` / check `status` before committing. Worth fixing
in the CLI too: `fangorn card` should leave the tracking directory at the new tip.

## 6. The old CLI shape lives on in sources

**Seen:** `fangorn commit <file> -m <msg>` → `error: unknown option '-m'` on CLI 0.4.0.
codex's `sources/seed.mjs`, which dev-intel's source started from, still passed it.

**Fix:** the template and guide examples use `fangorn commit <file>` only; a source helper in
westmarch (`commitAndPush(records, {namespace, replace})`) so each app stops re-writing the
CLI calls.

## 7. The checkout and the release disagree on the SDK

**Seen:** linking dev-intel to `~/fangorn/westmarch` (`file:`) made ship refuse: the CLI is SDK
`0.1.0-dev`, the checkout's `node_modules` reads with `2026.11.04-dev` (different contracts).
Hence the patch file instead of a link.

**Fix:** pin the SDK peer in `package.json`, and have `npm test` (or ship) print the SDK it
resolved, so a release isn't cut against a different contract set than the CLI users run.

## 8. The guide says the identity replaces the CID

`docs/app-to-agent.md` and the fangorn-app skill say the declared identity "replaces the CID as
the row id that `search` returns". It doesn't (see 1). Either fix the words or do the overhaul.

## 9. Proposal: an app's skill, installable from the index

`site.skill` already serves `skill/<app>/SKILL.md` and names its URL and sha256 in the card,
which the repo's `@card` anchors on chain. What's missing is the last step: a client verb that,
given an app found by `search`/`publishers`, reads its card, fetches the skill, checks the
sha256, writes it to the agent's skills directory, and adds the app's `/mcp`. With that, every
Fangorn app is a skill an agent can install on demand, and the index is the market.

- Only `SKILL.md` is served today. A skill with a script (dev-intel's `statement.mjs`) needs
  `site.skill` to take a directory, each file hashed into the card.
- Running a skill's script is running a stranger's code. Text-only skills need no sandbox; a
  skill that ships code needs either a pinned, hashed file the user approves once, or a
  sandbox (a VM / wasm runtime) before an index can install it unattended.

## 10. The card's fromBlock is the deployment block

`ship.js` says the repo's first block "becomes the card's fromBlock", but sets
`state.fromBlock ??= String(cfg.fromBlock ?? FangornConfig.fromBlock)`: the Fangorn deployment's
start (53592845 on Base Sepolia). dev-intel's state.json holds exactly that. Safe (nothing is
missed) but every reader scans from the deployment. Either record the block `repo init` landed in,
or fix the comment and the guide.
